# Guestbook with Prometheus & Grafana monitoring

This extends the Pulumi [Kubernetes Guestbook example](https://github.com/pulumi/examples/tree/master/kubernetes-ts-guestbook)
(the `simple/` variant) with monitoring. A single `pulumi up` creates:

- **An EKS cluster** (3 × `t3.medium`, default VPC) via `@pulumi/eks`. Optional: you can deploy to an existing cluster instead.
- **The Guestbook**: Redis leader, Redis replica and a 3-replica PHP frontend, in the `guestbook` namespace. Each pod now
  runs a Prometheus exporter sidecar.
- **kube-prometheus-stack** (Helm chart `92.3.1`) in the `monitoring` namespace: Prometheus Operator, Prometheus,
  Grafana, kube-state-metrics and node-exporter.
- **A `ServiceMonitor`** that tells Prometheus to scrape the Guestbook exporters.
- **Grafana on a LoadBalancer**, with a generated admin password and a provisioned **Guestbook dashboard**.

```
                         ┌──────────────── guestbook namespace ─────────────────┐
  browser ──► ELB ──►    │ frontend pod ×3     [php-apache :80 | apache-exporter :9117]
                         │ redis-leader pod    [redis :6379    | redis-exporter  :9121]
                         │ redis-replica pod   [redis :6379    | redis-exporter  :9121]
                         └───────────────▲──────────────────────────────────────┘
                                         │ scrape :metrics every 15s (ServiceMonitor "guestbook")
                         ┌───────────────┴─ monitoring namespace ──────────────┐
  browser ──► ELB ──►    │ Grafana ──► Prometheus ◄── kubelet/cAdvisor, kube-state-metrics
                         └─────────────────────────────────────────────────────┘
```

## How the Guestbook gets monitored

The Guestbook images don't expose Prometheus metrics themselves, so I left the images unchanged and added **exporter
sidecars**. Each one reads the app over `localhost` inside the same pod:

| Tier | Sidecar | Source | Example metrics |
|---|---|---|---|
| frontend | `lusotycoon/apache-exporter:v1.1.1` | Apache `mod_status` (`/server-status?auto`) | `apache_accesses_total` (requests), `apache_workers`, `apache_sent_kilobytes_total` |
| redis-leader / redis-replica | `oliver006/redis_exporter:v1.93.0` | Redis `INFO` | `redis_commands_processed_total`, `redis_connected_clients`, `redis_db_keys` |

- **Labels:** every Guestbook metrics Service is labelled `app.kubernetes.io/part-of: guestbook` and exposes a port named
  `metrics`. The `guestbook` ServiceMonitor selects on that label and port.
- **Frontend port split:** the frontend's metrics are on a separate ClusterIP Service (`frontend-metrics`), so the
  exporter is never exposed through the public load balancer.
- **Resource usage:** CPU, memory, network and restarts come from the kubelet/cAdvisor and kube-state-metrics scrapes
  that kube-prometheus-stack sets up.

## Prerequisites

- Pulumi CLI, logged in (`pulumi login`)
- Node.js 18+ and npm
- AWS credentials allowed to create EKS, EC2, IAM and ELB resources (`aws sts get-caller-identity` should work)
- `kubectl` (only for the verification steps)

## Deploy

```bash
npm install
pulumi stack init dev
pulumi config set aws:region us-west-2        # optional; us-west-2 is the default
pulumi up
```

`pulumi up` takes about 15–20 minutes, mostly EKS cluster creation.

### Optional configuration

| Key | Default | Purpose |
|---|---|---|
| `useExistingCluster` | `false` | `true` deploys to your current kubeconfig context instead of creating EKS |
| `serviceType` | `LoadBalancer` | Service type for Grafana and the frontend (`NodePort` for minikube/kind) |
| `instanceType` / `nodeCount` | `t3.medium` / `3` | EKS worker nodes |
| `grafanaAllowedCidrs` | `["0.0.0.0/0"]` | Source CIDRs allowed through the Grafana LB, e.g. `pulumi config set --path 'grafanaAllowedCidrs[0]' 203.0.113.4/32` |
| `grafanaAdminPassword` | random 20 chars | Set your own with `pulumi config set --secret grafanaAdminPassword ...` |

## Grafana access URL and admin credentials

The URL and credentials are stack outputs:

```bash
pulumi stack output grafanaUrl
pulumi stack output grafanaAdminUser                     # admin
pulumi stack output grafanaAdminPassword --show-secrets
```

Open `grafanaUrl` and log in. Then go to **Dashboards → Guestbook**. A new ELB's DNS name can take a minute or two to
resolve.

The admin password is generated by `random.RandomPassword` and stored encrypted in the stack state, so it isn't
written in this README. Other outputs: `frontendUrl` (the Guestbook itself), `prometheusService`, `eksClusterName`
and `kubeconfig` (secret).

## Verify that Prometheus is scraping the Guestbook

Point kubectl at the new cluster:

```bash
pulumi stack output kubeconfig --show-secrets > kubeconfig.json
export KUBECONFIG=$PWD/kubeconfig.json
```

**1. The ServiceMonitor exists and the exporters are running:**

```bash
kubectl -n monitoring get servicemonitor guestbook
kubectl -n guestbook get pods          # each pod shows 2/2 containers ready
```

**2. Prometheus shows the targets as UP.** Port-forward Prometheus and open
<http://localhost:9090/targets?search=guestbook>. The `serviceMonitor/monitoring/guestbook/0` pool should list
**5 targets**, all `UP`: 3 `frontend-metrics`, 1 `redis-leader` and 1 `redis-replica`.

```bash
kubectl -n monitoring port-forward svc/monitoring-kube-prometheus-prometheus 9090
```

**3. Or query it from the command line** (with the port-forward running):

```bash
curl -s 'http://localhost:9090/api/v1/query' --data-urlencode 'query=up{namespace="guestbook"}' \
  | jq -r '.data.result[] | "\(.metric.service)\t\(.metric.pod)\t\(.value[1])"'
```

Every row should end in `1`.

**4. Generate traffic and watch it show up.** Add a few guestbook entries in the browser, or run:

```bash
FRONTEND=$(pulumi stack output frontendUrl)
for i in $(seq 1 200); do curl -s -o /dev/null "$FRONTEND/"; done
```

Then query `sum(rate(apache_accesses_total{namespace="guestbook"}[1m]))` in Prometheus. Or watch the **Frontend
requests/s** and **Request rate by pod** panels on the Guestbook dashboard.

## The Guestbook dashboard (stretch goal)

`dashboards/guestbook.json` is loaded through a ConfigMap labelled `grafana_dashboard=1`. Grafana's dashboard sidecar
imports it automatically. Rows:

- **Overview:** frontend pods up, Redis instances up, total requests/s, Redis key count
- **Frontend (Apache):** request rate and bytes/s per pod, busy workers, worker scoreboard
- **Backend (Redis):** commands/s per service and per command, connected clients, memory
- **Pod resources:** CPU, memory working set, network and container restarts per pod

### Notes and limitations

- **Request counts:** Apache's `mod_status` counts all requests, including the exporter's own scrape of
  `/server-status` (about 1 every 15 s per pod). So the frontend never shows exactly zero.
- **No HTTP status codes:** `mod_status` doesn't report status codes, so there's no frontend error-rate panel. Getting
  one would mean instrumenting the PHP app or putting a proxy in front of it.
- **Disabled components:** alertmanager and the control-plane scrapes (scheduler, controller-manager, etcd, kube-proxy)
  are turned off. EKS manages and hides those components, so their targets would only show as down.
- **Images left as upstream:** the Guestbook images are unpinned and amd64-only, as in the upstream example. That's
  fine on EKS x86 nodes.
